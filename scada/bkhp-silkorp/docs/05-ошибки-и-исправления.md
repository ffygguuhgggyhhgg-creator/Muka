Проверено: 607 скриптов, 1419 тегов, 1859 объектов экрана, 323 привязки к
ПЛК и весовому терминалу. Методика и воспроизводимые проверки — в разделе 4.

Исправленные тексты скриптов лежат в `fixes/scripts/` (обязательные,
268 файлов) и `fixes/scripts-optional/` (по согласованию, 122 файла).
Порядок применения — `fixes/README.md`. **Ни один файл проекта не изменён:**
`project/` и `decoded/` — исходное состояние.

## 2. Обязательные исправления

### D-01 🔴 Аварийный останов включает механизмы

`AlarmStopButton_OnClick`. Нории останавливаются правильно
(`RelayOutN* := False`), а дальше:

```pascal
RelayOutC1.Value := True;          // аспирация 1 — ВКЛЮЧАЕТСЯ
...
RelayOutForwardT1.Value := True;   // транспортёр 1 вперёд — ВКЛЮЧАЕТСЯ
RelayOutReversT1.Value := True;    // и одновременно назад
```

Что `True` — это именно пуск, подтверждается независимо: `ManualStart`
выдаёт команду пуска как `RelayOutX.Value := True`, а `StopButtonX_OnClick`
останавливает как `RelayOutX.Value := False`. То есть нажатие аварийного
останова запускает 12 аспираций и подаёт на 18 транспортёров команды на
прямое и реверсивное вращение сразу.

**FIX-01:** 48 присваиваний `True` → `False`.

соответствующий объект, а 32 — нет; имена этих скриптов оставлены в
заводской нумерации, тогда как объекты пронумерованы сплошь.

| `StartButtonC2a_OnClick`, `StopButtonC2a_OnClick` | C6 | `StartButtonC6`, `StopButtonC6` | Аспирация 2а |
| `StartButtonN1a_OnClick`, `StopButtonN1a_OnClick` | N7 | `StartButtonN7`, `StopButtonN7` | Нория 1а |
| `StartButtonN2a_OnClick`, `StopButtonN2a_OnClick` | N8 | `StartButtonN8`, `StopButtonN8` | Нория 2а |

| `Start(Forward\|Revers)ButtonT17a_OnClick`, `StopButtonT17a_OnClick` | T15 | `…ButtonT15` | Транспортёр 17а |

который управляет тегами `T13` («Транспортёр 17»), а объект `…ButtonT13`
свободен. Если объекты нумеровались по индексу тега (как остальные 12 из 18),
то нужно переименовать `…ButtonT17_OnClick` → `…ButtonT13_OnClick`, а
`…ButtonT24_OnClick` → `…ButtonT17_OnClick`. **Перед переименованием
сверьте расположение кнопок на мнемосхеме** — из бинарного файла страницы

На странице есть объекты `T4CalButton1…5` и `T4CalButton7…10`, а вместо
`T4CalButton6` создан `T6CalButton16` — то есть кнопка калибровки задвижки
силоса 6-16 названа как кнопка группы Т6 с несуществующим номером 16.

пустить, ни остановить с экрана; кнопка теста сирены не работает; ещё
30 кнопок на мнемосхеме не делают ничего.

**Исправление только в редакторе** (переименование скриптов или объектов),
текстовой правкой не лечится. Исключение — `AlarmTest_OnClick`: в
`fixes/scripts/` он уже сохранён под правильным именем
`AlarmTestButton_OnClick` (FIX-06).

### D-03 🟠 Сброс аварий пишет не в тот тег

В проекте два похожих семейства тегов:

| Семейство | Группа | Кто пишет | Кто читает |
|---|---|---|---|
| `StatusAlarmN*`, `StatusAlarmT*` | Таймеры / … / Таймеры аварий | `MnemoControlN`, `MnemoControlT` | `MnemoControlN`, `MnemoControlT` |
| `AlarmStatusN*`, `AlarmStatusT*` | Статусы механизмов | `AlarmDropButton_OnClick` | **никто** |

Мнемосхема проверяет `StatusAlarmX`, а кнопка «Сброс аварии механизмов»
обнуляет `AlarmStatusX` — 27 тегов, которые никем не читаются. Авария
снимается только сама, по исчезновению входа `RelayAlarmX`.

**FIX-12:** 27 присваиваний `AlarmStatus*` → `StatusAlarm*`.

### D-04 🟠 Потеряно условие в контроле стоповых кнопок

`StopButtonsControl`, блоки норий и аспирации:

```pascal
if StatusN1.Value = 1 then            // только если механизм в работе (А)
begin
 if RelayStopInN1.AsBool = False then
   begin RelayOutN1.Value := False; StatusStartN1.Value := 16; end;
end;
```

Блоки транспортёров — те же 18 штук, но без внешнего условия
(на строках 219–220 видны подряд идущие комментарии
`//ТРАНСПОРТЕРЫ начало` и `//ТРАНСПОРТЕРЫ конец` — след неудачной вставки):

```pascal
//Транспортер 1 начало
begin                                  // ← здесь должно быть if StatusT1.Value = 1 then
 if RelayStopInT1.AsBool = False then
   begin ... StatusStartForwardT1.Value := 16; ... end;
end;
```

Следствие: пока цепь стоповой кнопки транспортёра не под напряжением,
скрипт каждую секунду переписывает `StatusStartForwardTn`/`StatusStartReversTn`
в 16. Заявка на пуск (код 5) не доживает до 20-й секунды в `ManualStart` —
транспортёр не запустится, и причина в журнале не видна.

**FIX-02:** во все 18 блоков вставлено `if StatusTn.Value = 1 then`.

### D-05 🟠 Ложный аларм при каждом нажатии кнопки задвижки

Все 194 обработчика кнопок задвижек построены так:

```pascal
if T6BlockSelectStatus.AsBool = False then
begin
  ...
  T6BlockSelectStatus.Value := True;              // сами ставим блокировку
  AddMessage(… 'Начало открытия задвижки …');
end;
if T6BlockSelectStatus.AsBool = True then         // видим СВОЮ же запись
  AddMessage(… mkAlarm, 'Активна блокировка пуска! Дождитесь выполнение операции…');
```

Второе условие проверяет флаг, который скрипт сам только что изменил,
поэтому аларм выдаётся **всегда** — и при успешном старте тоже. Журнал
(и PostgreSQL) забивается ложными авариями, оператор перестаёт им верить.

**FIX-03:** состояние блокировки снимается в локальную переменную
`BlockedBefore` до изменения флага:

```pascal
var
  BlockedBefore: Boolean;
begin
BlockedBefore := T6BlockSelectStatus.AsBool;
if BlockedBefore = False then ...
if BlockedBefore = True then AddMessage(…);
```

### D-07 🟡 Двойной инкремент времени калибровки

`T*CalScriptN`, такт 6: выход открытия включается и время открытия
инкрементируется в том же блоке, а следующий блок инкрементирует его ещё
раз, потому что выход уже стал `True`:

```pascal
if CalTimer > 5 then if CalTimer < 7 then
begin
  LatchRunOpen.Value := True;
  CalOpenTime.Value := CalOpenTime.Value + 1;   // ← лишний
end;
if CalTimer > 5 then if LatchRunOpen.AsBool = True then
  CalOpenTime.Value := CalOpenTime.Value + 1;
```

Время открытия завышается на 1 с и переносится в уставку тайм-аута
`9 + CalOpenTime` алгоритма открытия.

**FIX-04:** лишний инкремент убран в 65 скриптах.

## 3. По согласованию и рекомендации

### D-06 🟠 Пуск без предпусковой сигнализации (OPT-01)

`ManualStart` держит окно активности 120 с и выдаёт команды с 20-й секунды,
а сирену — только первые 10 с. Кнопка пуска ставит `ManualStartStatus := True`,
но таймеры не сбрасывает. Сценарий:

```
t=0    пуск нории 1 → сирена
t=20   нория 1 пущена
t=30   пуск транспортёра 5 → ManualTimerDelay = 30 >= 20
t=31   транспортёр 5 запущен БЕЗ предпусковой сигнализации
```

**OPT-01** (57 скриптов пуска): вместе с `ManualStartStatus := True` таймеры
обнуляются, то есть каждая новая заявка заново даёт 10 с сирены и 20 с
задержки. Побочный эффект: заявка, поданная в течение 20 с после предыдущей,
отодвигает пуск обеих на 20 с от последнего нажатия. Требует согласования
с регламентом объекта.

### D-08 🟠 Калибровка без тайм-аута (OPT-02)

В `T*OpenScriptN`/`T*CloseScriptN` тайм-аут есть (`> 9 + CalTime`), а в
`T*CalScriptN` — нет: единственный выход из алгоритма — срабатывание
концевика. Условие `CalTimer > 5 + CalOpenTime` не сработает, потому что
`CalOpenTime` растёт синхронно с `CalTimer`, пока выход открытия активен.
При неисправном концевике скрипт крутится бесконечно, а
`T*BlockSelectStatus = True` блокирует управление **всеми** задвижками
группы до перезапуска проекта.

**OPT-02** (65 скриптов): предельное время 600 с, по нему выход снимается,
блокировка сбрасывается, состояние задвижки — 5 «авария», сообщение в
журнал. Уставку 600 с надо согласовать с фактическим ходом задвижек.

### D-09 🟡 Код состояния 3 «Стоп (М)» недостижим

В `MnemoControlN/C/T` четыре ветви идут подряд, не через `else`. В ветви
`(RelayOut=1, RelayIn=0)` по истечении 3 с выполняется
`RelayOutX := False; StatusX := 3`, после чего **в том же проходе** срабатывает
ветвь `(0, 0)` и ставит `StatusX := 4`. Оператор никогда не видит «Стоп (М)»
после неуспешного пуска — только «Стоп (А)».

Автоматически не исправлено: непонятно, какое состояние задумано штатным.
Варианты — сделать ветви взаимоисключающими (`else if`) либо снимать выход в
конце блока. Решение за автором проекта.

### D-12 🟡 Задание частоты без ограничения

`T<n>FreqTarget`: `FreqToPLC := TargerFreq * 10000 / 50`. Ни в поле окна
`FreqWindow`, ни в скрипте нет проверки диапазона: ввод 100 Гц даёт 20000
в ПЛК (при шкале 0…10000 на 0…50 Гц). Рекомендуется задать в свойствах поля
границы 0…50 Гц и добавить в скрипт отсечение.

### D-16 🟠 Защита маршрутов не реализована

`T4BlockControl` — периодический скрипт, тело целиком закомментировано
(94 строки). Задумана проверка: если маршрут Т1-Т4 или Т2-Т4 собран
(зелёные `LineReversT1`/`LineForwardT1` и `LineT1Latch*`), а Т4 остановлен
(`ImageT4_1` красный) — остановить Т1/Т2 и соответствующую норию. Кнопка
`BlockControlButton` и индикатор `BlockControlMnemo` на экране есть, тег
`BlockControl` переключается, но ни одной блокировки за ним не стоит.

Логика опирается на **цвета объектов мнемосхемы** вместо тегов — это хрупко
(зависит от порядка выполнения скриптов отрисовки). При доработке
рекомендуется переписать условия через `StatusT*` и `T*LatchStatusByte*`.

Ни один тег аспирации (`RelayOutC*`, `RelayInC*`, `RelayStopInC*`) не
привязан к ПЛК. Кнопки, мнемосхема, сообщения и все 12 пар обработчиков
есть, но команда никуда не уходит, а `StatusC*` никогда не станет 1
«в работе», потому что `RelayInC*` всегда `False`. Аспирация управляется
«вслепую».

То же для транспортёров T8…T18: кнопки и обработчики есть (кроме мёртвых по
D-02), выходов нет.

Это и есть основной объём доработки проекта: 296 привязок OPC UA сделано,
для полного состава нужно ещё около 190 (14 аспираций × 3 + 11 транспортёров
× 5 + 4 нории × 4).

### D-22 🟠 Вход аварии не привязан у 6 норий

`RelayAlarmN*` привязан только у N1, N4, N6. У норий 2, 3, 5, 7, 8, 9 тег
читается в `MnemoControlN`, но всегда `False` — авария этих норий не
детектируется, `StatusAlarmN*` не поднимется, код состояния 10 «Авария»
недостижим.

### D-23 🟡 Тренды, архив и доступ не настроены

* `Trends.str` — один раздел и пустая «Группа 1»: тренды не настроены, хотя
  архив в PostgreSQL объявлен.
* `ArcSystem.sar` — 8 байт, настройки архивации по сути пустые.
* `Groups.seg` — 8 байт: группы доступа не заданы, то есть разграничения
  прав операторов нет, и `ConfirmMessage(GetClientName)` подтверждает
  сообщения от любого клиента.
* 14 тегов телеметрии ЧП (`T<n>Freq`, `T<n>Power`) не используются ни в одном
  скрипте — проверьте, что они выведены полями экрана, иначе токи и частоты
  нигде не видны.

### D-24 🟢 Мелкие замечания

* `Indicators` (периодический) и `StartVesIndicators` (при запуске) —
  почти дословный дубликат 60 строк; расходятся только способом чтения
  (`.Value = 1` против `.AsBool = True`) и обнулением `Capacity`.
  Логику стоит держать в одном скрипте.
* В `Indicators`/`StartVesIndicators` строки заданы двойными кавычками
  (`"Закрыта"`) — для Pascal это нетипично; проект компилируется, но лучше
  привести к одинарным.
* Опечатка в именах тегов: `T<n>TargerFreq` вместо `TargetFreq`
  (14 тегов). Переименование сломает совместимость — оставлено как есть.
* 214 периодических скриптов на такт 1 с (из них 195 — алгоритмы задвижек,
  каждый со своим счётчиком). Нагрузка на сервер растёт линейно с числом
  задвижек; при дальнейшем расширении логику стоит свернуть в один скрипт с
  циклом по индексу.
### D-25 🟡 Запись в статусные теги весового терминала

Три обработчика пишут в теги, которые терминал отдаёт только на чтение:

| Скрипт | Строка | Что происходит |
|---|---|---|
| `VesErrorOff_OnClick` | `L1_D1_S_Error.Value := 1` | «сброс ошибки» ставит ошибку (D-14) |
| `VesStartImage_OnClick` | `L1_D1_S_Start.Value := 1` | зажигает лампу «Пуск» в `Indicators`, команду терминалу не даёт |
| `VesStopImage_OnClick` | `L1_D1_S_Stop.Value := 1` | то же для лампы «Стоп» |

Объектов `VesStartImage` и `VesStopImage` на экране нет, поэтому последние
два скрипта не выполняются. Штатное управление циклом — через `L1_D1_Cmd`
(`VesInWork` = 2, `VesStopCircle` = 3), что и реализовано рабочими кнопками.
При доработке эти три скрипта следует либо удалить, либо перевести на
`L1_D1_Cmd` согласно протоколу Тензо-М.

## 4. Как проверено

Все выводы получены статическим анализом распакованного проекта, без
запуска SCADA. Инструменты в `tools/`, каждый запускается из корня
`scada/bkhp-silkorp`:

| Инструмент | Что делает |
|---|---|
| `parse_ssc.py` | разбор `Scripts.ssc`: 607 скриптов, тип запуска, привязки, 99.7 % байт файла |
| `parse_svrr.py` | дерево тегов из `Variables.svrr`: 64 группы, 1419 тегов, 100 % байт |
| `parse_svr.py` | привязки к OPC из `Variables.svr`: 1417 из 1419 записей |
| `check_tags.py` | чтения и записи каждого тега по всем скриптам; мёртвые теги, непривязанные входы/выходы |
| `check_index.py` | несоответствия индексов в однотипных скриптах задвижек (найдено 0) |
| `check_selfclobber.py` | шаблон «условие проверяет флаг, который скрипт сам изменил» (D-05, D-07, D-09, D-17) |
| `coverage.py` | матрица «тег → объект → обработчик → привязка к ПЛК» по всем механизмам |
| `apply_fixes.py` | генерация `fixes/` — каждая правка с проверкой шаблона, при несовпадении падает |
| `gen_docs.py` | справочные таблицы `docs/reference/` |

Проверки, давшие отрицательный результат (ошибок не найдено):

* индексы тегов во всех 194 скриптах кнопок и 195 алгоритмах задвижек
  соответствуют номеру задвижки в имени скрипта;
* подписи силосов и маршрутов согласованы между всеми скриптами одной
  задвижки — единственное расхождение D-20;
* ни один идентификатор в скриптах не остался неразрешённым (все 1419 тегов,
  1859 объектов, встроенные функции); из 5 «неизвестных» имён 4 — регистровые
  варианты цветовых констант, 1 — локальная переменная;
* формулы всех семи скриптов `T<n>FreqTarget` идентичны и без опечаток;
* распределение ламп задвижек 1–5 → `_1`, 6–10 → `_2` во всех семи группах
  выполнено верно (проверялось как возможная copy-paste ошибка);
* все привязанные выходы ПЛК пишутся хотя бы одним скриптом.
